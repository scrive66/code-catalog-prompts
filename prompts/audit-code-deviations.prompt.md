# 逸脱監査（多数派マトリクス監査）

前提: `docs/code-catalog.md`（プロンプト `/generate-code-catalog` で生成したカタログ）が存在すること。なければ先にそちらの実行を促して止まる。
あなたは監査者です。カタログの「確立した作法（採用率80%以上）」を物差しに、実コードを突き合わせ、
**多数派から外れている箇所**を候補として洗い出してください。ここで探すのは「チェックが無いこと自体が
バグ」という種類の欠陥です。通常の静的解析では拾えません。

## 入力（未指定なら既定値）

- 対象ファミリー: カタログの全ファミリー（1つに絞る指定も可。本文書の末尾に追記する形で指定する）
- 出力先: `docs/deviation-audit.md`（追記ではなく実行ごとに新規。既存があれば日付つきで別ファイル）

## 絶対ルール

1. **読み取り専用**。修正案は文章で提示するだけで、コードは変更しない。
2. **候補と断定を分ける**。全件「候補」として報告し、各候補に必ず反証チェックを通すこと（手順フェーズ3）。
3. **意図的な逸脱を除外する**。コメント・命名・テスト・設定ファイルで意図が確認できるものは
   「説明可能な逸脱」として分け、バグ候補に混ぜない。
4. 根拠のない危険度付けをしない。危険度は「差分の内容 × そのコードの重要度（外部入力を扱う、
   書き込みを行う、認証・課金・安全に関わる等）」で機械的に決める。

## 手順

### フェーズ1: 物差しの確定
カタログから「確立した作法」のチェック項目だけを監査項目として抜き出す。
「傾向あり（60〜79%）」以下の項目は、逸脱を責める根拠が弱いため監査対象にしない。

### フェーズ2: 突き合わせ
ファミリーごとに全実装を走査し、監査項目ごとに ○ / × を再集計する。
× の箇所をすべて候補リストに載せる（サンプリングで済ませない。母数が大きすぎる場合のみ、
その旨を明記して重要モジュールから優先走査する）。

### フェーズ3: 反証チェック（候補ごとに実施）
各候補について、バグ候補として残す前に次を確認する:
- その箇所専用のテストが存在し、チェック無しでも安全と言えるか
- 呼び出し側で同等のチェックを肩代わりしていないか
- フレームワークや共通ラッパが自動で担保していないか
- 過去のコミットメッセージやPR説明に意図の記録がないか（git log を参照できる場合）
1つでも「安全側の説明」が付いたら「説明可能な逸脱」へ移す。

### フェーズ4: 優先順位付け
残った候補に優先度を付ける:
- 高: 外部入力・書き込み・認証・金額・安全系の処理で、多数派の必須チェックが欠けている
- 中: 欠けていると障害・データ不整合につながり得る
- 低: ログ・書式など、動作には直結しない作法の逸脱

git 履歴が使える場合は補助シグナルを併記する: そのファイルの変更頻度、バグ修正コミットの有無、
最終変更からの期間。履歴シグナルは優先度の微調整にだけ使う。

## 出力フォーマット（docs/deviation-audit.md）

```markdown
# 逸脱監査レポート: <日付>
物差し: code-catalog.md（生成日 <日付>）の確立作法 N項目

## 優先度「高」の候補
| # | 箇所（path:line） | 欠けている作法 | 多数派の実例 | 反証チェック結果 | 想定リスク |
## 優先度「中」「低」の候補
（同形式）

## 説明可能な逸脱（バグ候補から除外したもの）
| 箇所 | 差分 | 安全と言える根拠 |

## 監査できなかった範囲
（走査を打ち切った箇所と理由）
```

## 完了報告
チャットには優先度「高」の候補だけを、各1行で返す（箇所と、欠けている作法）。
「高」が0件ならその旨と、「中」の件数だけを返す。

## やらないこと
- カタログに載っていない自分基準の作法違反の指摘
- 候補の自動修正、自動でのIssue化
- 「珍しい書き方」だけを理由にした候補化（多数派チェックの欠落が無いものは対象外）
